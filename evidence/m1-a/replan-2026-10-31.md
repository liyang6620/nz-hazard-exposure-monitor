## New resources and permissions

- Bootstrap adds `Storage Blob Data Contributor` for the signed-in repository
  owner at the production resource-group scope. This lets the owner stage the
  approved 217 MB reference and M3 gold Parquet from the local workstation with
  Entra authentication; shared storage keys remain disabled. This is a broad
  data-plane role within the production group and needs explicit review.
- Production adds `Storage Blob Data Contributor` for the GitHub managed
  identity on only the curated, gold and `$web` containers. It permits data
  staging and static frontend deployment, with no subscription-level role or
  new management permission. The existing ABAC allowlist already permits this
  role for a ServicePrincipal target.
- Production adds the `events-poison` queue for failed queue-trigger delivery
  and the `runtime` table for monitor activation and real publication latency.
  The existing queue/table data roles already cover both.
- The conditional production revision creates a separate Standard LRS host
  storage account with shared keys and anonymous access disabled. It holds
  `AzureWebJobsStorage` and the deployment package container. The Function
  system identity receives `Storage Blob Data Owner`, `Storage Queue Data
  Contributor` and `Storage Table Data Contributor` there. On the ADLS data
  account it retains only Contributor data roles. The bootstrap ABAC allowlist
  already permits the named roles only for ServicePrincipal targets.

The new host account and its operations add metered storage usage to the
previously estimated NZD 0.50-1.60 normal demonstration month. The bootstrap
state estimate remains NZD 0.01-0.10/month; guardrails are free. Actual costs
cannot be measured before deployment.

## Application and exposure changes

- The Azure Functions host now starts hourly housekeeping on deployment, runs
  the same core event processor from an `events` Queue Trigger, retries up to
  three deliveries, records terminal failures/timeouts and publishes after each
  assessment and housekeeping run. Reference and M3 Parquet are downloaded in
  bounded chunks to a warm temporary cache; DuckDB remains at 512 MB, one
  thread, with a 768 MB process guard. Approved source files must be staged
  before the Function package is deployed.
- Data publication uploads every file in a new `/data/generations/<id>/`
  directory first, then the immutable generation manifest, then
  `/data/manifest.json` last. The React build is uploaded separately to `$web`;
  deployments preserve live `data/` and `briefings/` content. The browser has no
  ArcGIS or OpenAI credential. LINZ browser-key configuration is still absent,
  so maps use attributed OpenStreetMap tiles.
- The existing public Storage website endpoint and public HTTPS Function
  endpoint are unchanged. There is no new HTTP trigger. The site deployer writes
  exact-path and directory `index.html` blobs for `/history`, `/method` and
  `/about`; each data publication adds them for every event detail route before
  replacing the manifest. Known direct links should therefore return HTTP 200.
  The `index.html` error document still returns HTTP 404 for unknown routes.
  Both status and browser rendering require Azure acceptance checks.
- Function settings add `NZHEM_ENV=azure`, a temporary data root, the 512 MB
  DuckDB and 768 MB process limits, the bundled offline DuckDB extension path,
  and `ARCGIS_PUBLISHER_ENABLED=false`.
  The owner must decide the sole ArcGIS publisher before enabling Azure.
- The current ignored `.env` notification recipient differs from the value
  used in the 26 Oct review plans. The three budget notifications and the two
  production Action Groups reflect that change; no address is printed here.
